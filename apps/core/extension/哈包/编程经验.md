## 一、数据格式兼容性：对象 vs 数组

### 问题
无名杀原生武将使用**数组格式**存储：
```js
shen_caocao: ["male", "wei", 3, ["guixin", "feiying"]]
// 访问技能列表：info[3] → ["guixin", "feiying"]
```

哈包扩展武将使用**对象格式**存储：
```js
moshusiji: { sex: "none", group: "ya", hp: 3, skills: ["huaqie", ...] }
// info[3] → undefined！必须 info.skills 才能访问
```

### 影响
框架 `player.reinit(from, to)` 内部使用 `info[3]`（数字下标）读写技能列表来执行技能移除/添加。对于对象格式的武将数据，`info[3]` 永远是 `undefined`，导致 `reinit` 内部的技能替换循环**静默跳过**——不报错也不执行。

### 解决方案
**在 `reinit` 前后手动处理技能替换。** 必须用 `info.skills`（属性名）而非 `info[3]`（数字下标）读取技能列表。

```js
// 手动移除旧技能
const oldInfo = lib.character[oldName];
if (oldInfo?.skills) {
    for (const s of oldInfo.skills) target.removeSkill(s);
}
// reinit 处理基本属性（name, sex 等）
await target.reinit(oldName, newChar, null, true);
// 手动添加新技能
if (newInfo.skills) {
    for (const s of newInfo.skills) target.addSkill(s);
}
```

### 教训
**任何调用 `reinit` 且涉及对象格式角色的场景，都必须手动处理技能替换。**

## 二、viewAs 技能的构成要素

### 问题
最初 `qiaoshou_shan` 只写了 `viewAs: { name: "shan" }`，缺少关键配置，导致技能无法触发。

### viewAs 的完整配置模式

| 属性 | 作用 | 缺失的后果 |
|------|------|-----------|
| `enable: ["chooseToRespond", "chooseToUse"]` | 声明哪些场景可触发 | 技能不出现候选列表 |
| `viewAs: { name: "shan" }` | 定义视为的牌 | 核心定义 |
| `filterCard(card)` | 筛选可用牌 | 无法过滤牌类型 |
| `viewAsFilter(player)` | 是否有可用牌 | 技能图标常亮/常灰 |
| `position: "hes"` | 可选牌的区域 | 默认只有手牌区 |
| `check(card)` | AI 选牌评分 | AI 无法正确选牌 |
| `prompt` | 技能提示文字 | 无提示 |
| `ai.respondShan: true` | AI 知道能当闪 | AI 不出闪 |

### 关键发现
- `position: "hs"` = 手牌区 + 特殊区，**不含装备区**
- `position: "hes"` = 手牌区 + 装备区 + 特殊区，**含装备区**
- `round: 1` **不能**直接写在 viewAs 技能上，会导致冲突。必须改为手动 storage 标记 + reset 子技能模式。

### 教训
**实现 viewAs 技能时，按上述 8 个属性逐项检查，缺一不可。**

## 三、filter 中调用 canUse 的致命陷阱

### 问题
`canUse("sha")` 在技能的 `filter` 中调用会导致空引用崩溃。错误栈中 `inRange` 中某玩家的 `hasSkill` 因玩家引用为 `undefined` 而失败。

### 原因
`filter` 在触发编排阶段（`arrangeTrigger`）被执行。此时游戏的事件上下文可能尚未完整初始化，距离计算链（`inRange → targetInRange`）中某些玩家对象引用可能为 undefined。

### 解决方案

| 阶段 | 可做什么 | 不可做什么 |
|------|----------|------------|
| `filter` | 轻量判断（牌名、手牌数、标记等）| `canUse()`、`inRange()`、距离相关 |
| `cost` | 完整判断（`canUse`、`chooseXXX`）| — |

将 `canUse` 检查移到 `cost` 开头：
```js
filter(event, player) {
    return player.countCards("h", "sha") > 0;  // ✅ 轻量替代
},
async cost(event, trigger, player) {
    if (!player.canUse("sha")) return;  // ✅ cost 上下文安全
    // ...
}
```

### 教训
**filter 中只放不依赖完整事件上下文的轻量判断。所有涉及距离/范围/可用性的检查放到 cost 中。**

## 四、手牌上限 + 弃牌保护 = 真正的"不计入上限"

### 问题
只写 `ignoredHandcard: card => true` 会让锦囊牌不占手牌上限，但弃牌阶段时玩家仍然可以弃置锦囊牌而保留更多基本牌和装备牌，违背"锦囊牌不计入上限"的设计意图。

### 完整方案
两个 mod 必须同时存在：
```js
mod: {
    ignoredHandcard(card, player) {
        if (get.type(card, "trick") === "trick") return true;  // 不占上限
    },
    cardDiscardable(card, player, name) {
        if (name === "phaseDiscard" && get.type(card, "trick") === "trick") return false;  // 弃牌阶段不可弃
    },
}
```

### 教训
**"不计入手牌上限"的正确实现 = `ignoredHandcard` + `cardDiscardable("phaseDiscard", false)`。两者缺任一逻辑都不完整。**

## 五、概率模型设计

### 问题
"随机锦囊牌"有两种理解，概率分布完全不同：

| 方式 | 实现 | 概率 |
|------|------|------|
| 从牌堆随机抽 | `get.cardPile(type === "trick", "random")` | 按牌张数加权（过河拆桥 6 张 > 无中生有 2 张） |
| 随机牌名再抽 | `lib.inpile → filter → randomGet → get.cardPile(name)` | 每种牌名等概率 |

### 教训
**实现"随机获得一种牌"的技能效果之前，先和设计者确认是"按张数加权"还是"按牌名等概率"。两者语义不同，概率分布完全不同。**

## 六、多效果共用状态的设计模式

### 背景
巧手有三个子效果，每轮各可发动一次。需要：
- 三个效果各自独立判断是否已发动
- 共用一个父技能标记展示状态
- 每轮开始时统一重置

### 实现模式

```js
// 父技能：mark + intro 展示
qiaoshou: {
    mark: true,
    intro: {
        content(storage, player) {
            return [
                player.storage.qiaoshou_judge_round ? "已发动" : "可发动",
                player.storage.qiaoshou_view_round ? "已发动" : "可发动",
                player.storage.qiaoshou_shan_round ? "已发动" : "可发动",
            ].join("/");
        },
    },
    group: ["qiaoshou_judge", "qiaoshou_view", "qiaoshou_shan", "qiaoshou_reset"],
},

// 复位子技能：silent 不弹窗
qiaoshou_reset: {
    trigger: { global: "roundStart" },
    silent: true,
    content() {
        delete this.player.storage.qiaoshou_judge_round;
        delete this.player.storage.qiaoshou_view_round;
        delete this.player.storage.qiaoshou_shan_round;
    },
},

// 子技能：在 content 中设置标记
async content(event, trigger, player) {
    player.storage.qiaoshou_judge_round = true;  // 标记已发动
    // ...
},
```

### 关键点
- `silent: true` — 复位技能不弹窗不日志
- `this.player` 而非 `player` — 在 `content()`（非 async）中需用 `this.player`
- 子技能 filter 中检查 `player.storage.xxx_round` 来控制本轮是否可触发
- 父技能的 `group` 包含所有子和复位子

### 教训
**`round: 1` 只能用在简单技能上。多效果共享状态、viewAs 技能等复杂场景，改为手动 storage 标记 + 复位子技能模式。**

## 七、chooseXXX 的取消支持

### 问题
`chooseCard("h", true, ...)` 中的第二个参数 `true` 表示**强制选择**（不可取消），去掉后用户可点击取消。

### 常用模式

```js
// 强制选择（锁定技效果，不可跳过）
player.chooseCard("h", true, "请选择一张牌")

// 可选选择（主动技效果，允许取消）
player.chooseCard("h", "请选择一张牌（可取消）")

// choosePlayerCard 同样
player.choosePlayerCard(target, "hej")  // 可取消
player.choosePlayerCard(target, true, "hej")  // 不可取消
```

### 教训
**锁定技效果用 `true`（强制），主动技/子效果用无参数（允许取消）。先明确技能性质再决定。**

## 八、Git 工作流陷阱

### 问题 1：PowerShell 与 Bash 语法差异

| 操作 | Bash | PowerShell |
|------|------|------------|
| 链式命令 | `cmd1 && cmd2` | `cmd1; cmd2`（不能用 `&&`）|
| heredoc | `cat <<'EOF' ... EOF` | 不支持，用多个 `-m` 参数 |
| 多行 commit | `-m "$(cat <<'EOF'...)"` | `-m "line1" -m "line2" -m "line3"` |
| 路径通配 | `dir "ext/哈包/**"` | `Get-ChildItem -Path "ext/哈包" -Recurse` |

### 问题 2：`.gitignore` 屏蔽
`apps/core/.gitignore` 中有 `extension/**` 规则，会屏蔽扩展目录下新增的未跟踪文件。务必用 `git add -f` 添加强制添加。

### 问题 3：LF/CRLF 警告
Windows 环境下提交会触发 `LF will be replaced by CRLF` 警告，**无害但烦人**，属于 git 的跨平台行尾转换机制。

### 教训
**PowerShell 终端下，`&&` 链式命令用 `;` 替换，多段 commit message 用多个 `-m`。扩展目录新文件一律用 `-f` 强制添加。**

## 九、变量命名一致性

### 问题
```js
const targetResult = await player.chooseTarget(...).forResult();
if (!result.bool || ...)  // ❌ result 未定义！应该是 targetResult
```

`chooseXXX` 返回值赋给了 `targetResult`，但判断时写了 `result`，导致 `ReferenceError: result is not defined`。

### 教训
**所有 `.forResult()` 的返回值立即赋给命名一致的变量，并在下一行立即校验。不要跨行忽略变量名。**

## 十一、子事件缺少父事件属性（`trigger` 层级错误）

### 问题
触发时机为子事件的技能（如 `useCardToBefore`），`trigger` 是子事件对象，其上没有父事件才有的属性。

```js
// kuihua 触发时机: useCardToBefore
trigger: { player: "useCardToBefore" }

// 错误：直接存子事件
player.storage._kuihua_trigger = trigger;
// 后续访问 useTrigger.directHit → undefined!（directHit 挂在父事件 useCard 上）
```

### 原因
某些事件属性只存在于父事件上，子事件只是父事件流程中的一个阶段。例如 `directHit` 数组挂载在 `useCard` 事件上，`useCardToBefore` 子事件上没有。

### 解决方案
```js
// 修复：存父事件
player.storage._kuihua_trigger = trigger.getParent();
```

**常见缺少属性的子事件：**
| 子事件 | 缺少的属性 | 属性的位置 |
|--------|-----------|-----------|
| `useCardToBefore` | `directHit` | `trigger.getParent()` (useCard) |
| `damageBegin` 前系列 | `card`（部分场景） | `trigger.getParent()` |

### 教训
**存储 trigger 到 storage 供后续技能使用时，先确认后续需要的属性是否在当前事件层级。子事件触发时机 → 优先 `trigger.getParent()`。**


## 十二、`forResult()` 返回值可能为 `undefined`

### 问题
`judgeEvent.forResult()` 在某些边界情况下（如判定目标已阵亡、牌堆无牌）可能返回 `undefined`，直接访问 `.bool` 会报 `TypeError: Cannot read properties of undefined`。

```js
// 错误
const result = await judgeEvent.forResult();
if (!result.bool) { ... }  // ❌ result 可能为 undefined
```

### 解决方案
```js
// 修复：先判空
const result = await judgeEvent.forResult();
if (result && !result.bool) { ... }  // ✅
```

### 教训
**所有 `.forResult()` 的返回值在使用属性前必须判空。如判定失败无后果，等同于 `result.bool === false` 处理即可。**


## 十三、废除/重来类递归需固定目标

### 问题
技能中"废除结果并重新执行"的递归模式，如果重新执行时会再次 `chooseTarget` 选人，会导致目标漂移——废除者可以换一个对手。

### 解决方案
将原目标通过参数传入，递归时跳过选择步骤：

```js
// 函数签名增加可选参数
async function executeSkill(initiator, depth, fixedTarget = null) { ... }

// 首次调用：正常选人
if (!fixedTarget) {
    target = await initiator.chooseTarget(...).forResult();
} else {
    target = fixedTarget;  // 递归时使用固定目标
}

// 废除时传入对手
const opponent = vetoer === initiator ? target : initiator;
await executeSkill(vetoer, depth + 1, opponent);
```

### 教训
**递归重来的技能，必须确保重来时对手不变。首次调用传 null 走选人逻辑，递归时传原对手跳过选人。**


## 十四、触发时机名 vs 事件名：必须用框架传入的第三参数

### 问题
技能同时监听两个触发时机（如 `useCard` 和 `damageBegin3`），在 `filter` 和 `content` 中写出以下代码：

```js
trigger: { player: "useCard", source: "damageBegin3" },
filter(event, player) {
    if (event.name === "useCard") ...      // ✅ useCard 恰好是事件名
    if (event.name === "damageBegin3") ...  // ❌ false! event.name 是 "damage"
},
async content(event, trigger, player) {
    if (trigger.name === "useCard") ...      // ✅ useCard 恰好是事件名
    if (trigger.name === "damageBegin3") ... // ❌ false! trigger.name 是 "damage"
}
```

### 原因
框架的触发时机名（triggername，如 `damageBegin3`）不等于事件名（event name，如 `damage`）。`trigger.name` / `filter` 的第一个参数 `event` 是被触发的事件本身——对于 `damageBegin3` 时机，事件是 `damage` 事件。

`useCard` 恰好事件名和触发时机名一致，所以用 `trigger.name` 蒙对了；但 `damageBegin3` 这种情况就失效。

### 解决方案

```js
// filter: 用第三个参数 name（框架传入的 triggername）
filter(event, player, name) {
    if (name === "useCard") ...
    if (name === "damageBegin3") ...
},

// content: 用 event.triggername（框架写入当前技能事件）
async content(event, trigger, player) {
    if (event.triggername === "useCard") ...
    if (event.triggername === "damageBegin3") ...
}
```

### 教训
**多时机触发的技能，永远用 `filter(event, player, name)` 的第三个参数和 `event.triggername` 来区分时机，不要依赖 `trigger.name` / `event.name`。这两个是不等于触发时机名的。**


## 十五、viewAs 技能的 content 不执行 + 限制方式

### 问题
`enable: "chooseToUse"` + `viewAs: { ... }` 的技能，写了 `content` 永远不会执行。追踪"已使用"的 storage 永远不设值，导致 `viewAsFilter` 永远返回 true，技能可无限使用。

```js
// ❌ content 是死代码
{
    enable: "chooseToUse",
    viewAs: { name: "wuxie" },
    viewAsFilter(player) {
        if (player.storage.xxx >= game.roundNumber) return false;
        return true;
    },
    async content(event, trigger, player) {
        player.storage.xxx = game.roundNumber;  // 永远不会执行！
    },
}
```

### 原因
viewAs 技能走 `useCard → useResult` 路径，框架直接创建虚拟牌并 useCard；`content` 只在 `useSkill` 路径下执行。整个 codebase 中没有一个 `enable: "chooseToUse" + viewAs` 的技能同时有 `content`。

### 解决方案
**直接使用框架内置的 `round: 1` 或 `usable: 1`：**

```js
// ✅ 最简单：框架自动管理计数
{
    enable: "chooseToUse",
    viewAs: { name: "wuxie" },
    round: 1,  // 每轮一次，框架自动计数 + 自动重置
    viewAsFilter(player) {
        return true;  // 不再需要手动判断
    },
}
```

`round` 和 `usable` 对 viewAs 技能是直接生效的，框架会在 `useCard` 时自动计数。

### 教训
**viewAs 技能的 content 不执行。限制次数直接用 `round: 1` 或 `usable: 1`，框架自动处理，不需要手动 storage 追踪。**


## 十六、`filterCard: false` 布尔值的致命陷阱

### 问题
```js
filterCard: false,  // ❌ 布尔值 false 被框架解释为"不过滤"
selectCard: -1,     // 全选所有通过 filter 的牌（即所有手牌！）
```

结果：发动技能时所有手牌被消耗。

### 原因
框架处理 `filterCard` 时，布尔值 `false` 和函数 `() => false` 语义不同：
- `filterCard: false`（原始布尔）→ 框架认为是"没有过滤函数"→ 所有牌通过
- `filterCard() { return false; }`（函数） → 正常调用筛选，明确拒绝所有牌

### 解决方案
必须写成函数形式：
```js
filterCard() {
    return false;
},
```

### 教训
**`filterCard: false` 不等于"拒绝所有牌"。任何需要明确拒绝牌的 filterCard 必须写成函数 `return false`。**


## 十七、`round: 1` 与 `usable: 1` 的选择

### 区别

| 属性 | 含义 | 重置时机 | 适用场景 |
|------|------|----------|----------|
| `round: 1` | 每轮限一次 | `roundStart` | 全局节奏控制 |
| `usable: 1` | 每回合限一次 | 每个角色的回合开始时 | 与回合相关的触发 |

### 何时可替代手动 storage 追踪

以下模式可完全替换：
```js
// ❌ 手动模式
if (player.storage.xxx_round >= game.roundNumber) return false;  // filter
player.storage.xxx_round = game.roundNumber;                      // content

// ✅ 内置模式
round: 1,  // 或 usable: 1
```

### 不可替换的场景

当技能有多功能分立时（如主技能追踪 X 值 + 摸牌），直接在父技能加 `usable: 1` 会阻断所有功能。此时必须拆为子技能：
```js
mainSkill: {
    group: ["mainSkill_draw"],
    // 不用 round/usable，永远触发（追踪状态用）
    async content() { /* 追踪 X 值、维护状态 */ }
},
subSkill: {
    mainSkill_draw: {
        usable: 1,          // 只在子技能上加限制
        priority: -1,       // 确保主技能先执行
        filter() { /* 检查状态 */ },
        async content() { /* 摸牌 */ },
    },
}
```

### 教训
**优先用 `round` / `usable`。多功能的技能不能加在父技能上，必须拆子技能后各自加限制。`priority: -1` 确保子技能在同批次触发中后执行（父技能先更新状态）。**


## 十八、cost 与 content 的 event.result 隔离

### 问题
触发技能中 `cost` 写入 `event.result`，`content` 中读取 `event.result` 得到 `undefined`：

```js
async cost(event, trigger, player) {
    event.result = await player.chooseControl(...).forResult();
    return event.result.control !== "cancel2";
},
async content(event, trigger, player) {
    const choice = event.result.control;  // ❌ Cannot read properties of undefined!
}
```

### 原因
`cost` 运行在 `[技能名]_cost` 事件中，`content` 运行在独立的 `[技能名]` 事件中。两个事件各有自己的 `result`，互不共享。

### 解决方案
框架支持通过 `cost_data` 传递数据：
```js
async cost(event, trigger, player) {
    const result = await player.chooseControl(...).forResult();
    event.result = {
        bool: result.control !== "cancel2",
        cost_data: { control: result.control },  // 传给 content
    };
},
async content(event, trigger, player) {
    const choice = event.cost_data.control;  // ✅ 用 cost_data 读取
}
```

### 教训
**cost 向 content 传递数据的唯一方式是 `event.result = { bool, cost_data: { ... } }` 模式。content 中通过 `event.cost_data.xxx` 读取。**

## 二十、扩展卡牌的距离属性不自动生效

### 问题
义体卡通过 `lib.card.list.push()` 直接推入牌堆，但卡牌数据中的 `distance` 属性（如武器的 `attackFrom: -2`、坐骑的 `globalFrom: -2`）不会像普通装备那样自动生效。因为引擎只在装备栏（`player.getEquips("e")`）中读取装备牌的距离修正，而义体卡存储在 `player.storage._yiti_mark` 中。

### 解决方案
在 `_yiti_mark` 技能中添加 `mod` 处理器，手动遍历已装备义体并累加距离：

```js
_yiti_mark: {
    mod: {
        globalFrom(from, to, distance) {
            const list = getYitiList(from);
            let delta = 0;
            for (const item of list) {
                const info = lib.card[item.name];
                if (info?.distance && typeof info.distance.globalFrom === "number") {
                    delta += info.distance.globalFrom;
                }
            }
            return distance + delta;
        },
        attackFrom(from, to, range) {
            // 同理累加 attackFrom
        },
    },
},
```

### 教训
**任何绕过引擎标准存储路径（装备栏 → storage）的卡牌数据，其 `distance` 属性都需要自己在技能 mod 中手动计算。`globalFrom` 影响全体距离，`attackFrom` 影响攻击距离，两者需要分别处理。**


## 二十一、`precontent` 不可强制覆盖配置

### 问题
`precontent` 每次页面加载都执行。原代码中 `!lib.config.characters.includes(PACK_NAME)` 每次都为 `true`（因为用户关闭了），于是又把武将/卡牌强制加回并 `game.saveConfig`。用户关闭开关后刷新页面，设置又被覆盖。

`isNewPack` 模式（用 `lib.config.all.characters.includes` 判断首次安装）也无效，因为 `lib.config.all.*` 不是持久化配置——每次页面加载由各扩展的 precontent 重新构建，旧扩展不运行时 `all` 里就没有它，导致判断永远为 `true`。

### 正确方案
**去掉所有强制启用逻辑**。`precontent` 只负责：
1. 注册到 `lib.config.all.*`（让包出现在菜单可选列表）
2. 根据**已有配置**（`lib.config.characters.includes` / `lib.config.cards.includes`）决定是否注册数据
3. 绝不调用 `game.saveConfig("characters", ...)` 或 `game.saveConfig("cards", ...)`

```js
// ✅ 只注册到可选列表，不修改启停状态
if (!lib.config.all.characters.includes(PACK_NAME)) {
    lib.config.all.characters.push(PACK_NAME);
}
// 仅在已启用时才注册实际角色数据
if (lib.config.characters.includes(PACK_NAME)) {
    Object.assign(lib.character, allCharacters);
    lib.characterPack[PACK_NAME] = allCharacters;
}
```

### 教训
**`precontent` 不应修改 `lib.config.characters` / `lib.config.cards`。启用/禁用交给菜单 UI 和引擎的标准流程。扩展只负责"我能提供什么"，不负责"是否启用"。**


## 二十二、武将双路径加载

### 问题
关闭武将包后武将仍在卡池。根因是引擎每局开始时**无条件遍历 `lib.characterPack`**：

```js
for (let i in lib.characterPack) {
    for (let j in lib.characterPack[i]) {
        lib.character[j] = lib.character[j] || lib.characterPack[i][j];
    }
}
```

即使 `lib.character` 中不注册（`Object.assign` 被跳过），引擎也会从 `lib.characterPack` 中把角色拉回来。

### 修复
两者必须同时条件化：
```js
if (lib.config.characters.includes(PACK_NAME)) {
    lib.characterPack[PACK_NAME] = allCharacters;  // 引擎遍历源
    Object.assign(lib.character, allCharacters);     // 直注册
}
```

### 教训
**`lib.characterPack` 不受 `config.characters` 控制，每局无条件加载。扩展武将包必须同时管理 `characterPack` 和 `character` 两处注册。**


## 二十三、牌堆条目残留

### 问题
`lib.card.list.push()` 直接写入的条目，在用户关闭卡牌包后不会自动清除——引擎每局重建牌堆时只遍历 `lib.cardPackList`，不认识扩展直接 push 的条目。

### 修复
每次 precontent 开头先清理旧条目：
```js
const names = new Set(Object.keys(yitiCards));
for (let i = lib.card.list.length - 1; i >= 0; i--) {
    if (names.has(lib.card.list[i][2])) {
        lib.card.list.splice(i, 1);
    }
}
// 然后再根据 config.cards 决定是否 push
```

### 教训
**`lib.card.list` 是持久化的全局牌堆，扩展写入的任何条目在包关闭后不会自动消失。必须自己写清理逻辑，在每次 precontent 开头先移除再按配置加回。**


## 二十四、`chooseToDisable` 的 AI 签名

### 问题
```js
player.chooseToDisable(true)
    .set("ai", event => {
        const list = event._controls || [];  // ❌ event._controls 是 undefined
        return list.randomGet();  // 永远返回 undefined
    })
```
AI 回调签名为 `(event, player, list)` ——**第三个参数才是可选装备栏列表**。错误写法导致 `list` 永远为空数组，AI 选不出结果，技能无限重试。

### 正确写法
```js
.set("ai", function (event, player, list) {
    if (list.includes("equip2")) return "equip2";
    if (list.includes("equip5")) return "equip5";
    return list.randomGet();
})
```

### 教训
**`chooseToDisable` AI 回调三个参数：`(event, player, list)`。第三个参数 `list` 才是可选列表，不是 `event._controls`。**


## 二十五、`lib.skill.global` 的 API

### 问题
`lib.skill.global.has("skillName")` → `TypeError: lib.skill.global.has is not a function`

### 原因
`lib.skill.global` 是这个版本的类数组对象，API 是 `.add()` / `.remove()` / `.includes()`，**没有 `.has()`**。

### 教训
**使用全局技能管理时，判断技能是否存在用 `lib.skill.global.includes("skillName")`，不是 `.has()`。**


## 二十六、`ai.result` 静态正值导致 AI 无限循环

### 问题
```js
ai: { result: { player: 2 } }
```
AI 每次扫描可选技能都得到正值 2，只要 `filter` 还通过就会反复发动，直到资源耗尽。游戏看起来像卡死。

### 修复
改为动态函数，在资源不足时返回 0：
```js
ai: {
    result: {
        player(player) {
            if (player.countCards("h") <= 2) return 0;
            return 1;
        },
    },
},
```

### 教训
**有消耗的技能（弃牌、废装备栏等）的 `ai.result` 必须用函数，在资源不足时返回 0 或负值。静态正值 = 无限循环。**


## 二十七、Git 忽略规则的多层级结构

### 问题
文件被忽略但找不到原因。需要知道项目有多个 `.gitignore` 层级：
- `apps/core/.gitignore` → `extension/**` 屏蔽所有扩展，然后用 `!extension/哈包/**` 排除
- `packages/extension/.gitignore` → `*/` 屏蔽 `packages/extension/` 下子目录，和 `apps/core/extension/` 无关
- 根目录 `.gitignore` → 不含哈包相关规则

### 关键命令
```bash
git check-ignore -v "path/to/file"    # 查文件被哪条规则忽略
git ls-files --others --exclude-standard  # 列未追踪且非忽略的文件
git add -f "file"                          # 强制添加被忽略的文件
```

### 教训
**扩展目录下的新文件默认被 `apps/core/.gitignore` 的 `extension/**` 忽略，首次提交务必 `git add -f`。`packages/extension/.gitignore` 的 `*/` 只影响它所在的那个目录，不要和 `apps/core/extension/` 混淆。**


## 二十八、vscode/ide 未追踪文件不可见

### 问题
IDE 的源代码管理面板默认不显示 `.gitignore` 中排除的文件。导致 56 张图片文件完全没有出现在修改列表中，肉眼可见目录结构完整就误以为已追踪。

### 教训
**永远不要依赖 IDE 面板判断是否已追踪。必须用 `git ls-files -- "path/"` 和 `git ls-files --others --exclude-standard` 双重确认。图片等二进制文件更容易被忽略——因为它们没有语法错误提示，隐蔽性更高。**
