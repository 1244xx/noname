# 武将与技能编写指南

## 文档目的

这份文档不是讲“怎么调试 bug”，而是讲：

- 在 `Zusfylri武将包` 这套新架构里，应该怎么写一个武将
- 新架构和旧架构的真正区别是什么
- 哪些写法在当前引擎里更稳
- 哪些写法虽然看起来现代，但在无名杀里更容易炸

这份文档的目标是让后续开发尽量做到：

- 写的时候就少踩坑
- 少返工
- 少把问题留到实机阶段才暴露

---

## 一、先理解当前项目结构

当前扩展的主入口是：

- `D:\app\noname\resources\app\extension\Zusfylri武将包\extension.js`

当前实际开发主路径是：

- `D:\app\noname\resources\app\extension\Zusfylri武将包\module\*.js`

聚合出口是：

- `D:\app\noname\resources\app\extension\Zusfylri武将包\character\index.js`

典型单个模块里通常同时包含：

- `character`
- `skill`
- `translate`
- `title`
- `sort`

也就是说，一个模块通常对应一个武将或一组强相关武将，而不是像旧结构那样把技能、翻译、角色完全拆散。

---

## 二、新架构和旧架构到底差在哪

## 1. 旧架构是什么

旧架构更接近原生无名杀扩展写法，常见形态是：

- `extension.js` 逐个加载 `skill/*.js`
- 每个技能文件直接 `game.import("character", function(lib, game, ui, get, ai, _status){ ... })`

它的优点是：

- 更贴原生加载方式
- `lib / game / ui / get / _status` 天然在上下文里
- 文件短
- 技能写法朴素
- 少一层桥接，少一层运行时错位

它的缺点是：

- 模块组织差
- 重复代码多
- 公共逻辑不容易沉淀
- 包一大就难维护

## 2. 新架构是什么

当前新架构是：

- 外层模块化组织
- 统一聚合角色、技能、翻译
- 更适合长期维护一个大包

它的优点是：

- 结构清晰
- 模块边界更明确
- 更容易统一规范
- 更容易沉淀公共函数和安全层

它的缺点是：

- 在无名杀当前引擎里，运行时对象不稳定的问题会被放大
- `lib / game / ui / get / _status` 不一定在每个时点都稳
- StepCompiler 会吃掉局部 helper 和跨 step 变量
- 新架构比旧架构更依赖开发者自己做安全兜底

## 3. 最重要的结论

当前项目最稳的取舍不是“纯旧”也不是“纯新”，而是：

`外层保持新架构组织，内层技能尽量按旧架构那种朴素、原生、少桥接的方式写。`

这句话非常重要。后续写技能时要一直记着。

---

## 三、推荐开发原则

## 1. 外层模块化，内层少抽象

推荐：

- 模块继续放在 `module/*.js`
- 但技能内部不要过度抽 helper 链
- 尤其不要为了“优雅”把本来很短的技能拆成很多跨层桥接

不推荐：

- 技能内部大量依赖模块外层 helper
- 技能内部大量依赖桥接层再转发
- 技能内部把本来一步能取到的运行时对象绕很多层再取

## 2. 先写“能稳定跑的技能”，再追求“漂亮”

在无名杀里，稳定性优先级高于抽象美感。

优先顺序应该是：

1. 技能能稳定加载
2. 技能能稳定触发
3. 技能能稳定结算
4. UI 与文案正确
5. AI 合理
6. 最后才是代码形式够不够漂亮

## 3. 能贴官方模板，就尽量贴官方模板

尤其是以下几类：

- 开局技
- `viewAs` 技
- 主公技
- 限定技
- 标记技
- 选择按钮类技能

如果官方包里已经有非常接近的成熟模板，优先对齐它，不要先自创一套结构。

---

## 四、推荐的开发流程

写一个新武将，建议按这个顺序：

1. 先确定武将信息
- 性别
- 势力
- 体力/体力上限/护甲
- 武将图片
- 武将排序和标题

2. 再确定技能分类
- 锁定技
- 主动技
- 触发技
- 转化技
- 标记技
- 主公技
- 限定技

3. 先找官方或旧包最接近模板
- 不要先空手起结构
- 先决定“这招像谁”

4. 先写最小可跑版本
- 先确保能触发和结算
- 不要第一版就把 AI、日志、花式 UI 一起写满

5. 再补：
- 文案
- 标记说明
- AI
- 特效/日志

6. 最后做实机单测

## 五、角色数据怎么写

## 1. 当前模块里的基本结构

推荐保持这种组织方式：

```js
window.zusfylriModules["example"] = {
    key: "example",

    character: {
        zus_example: char("male", "wei", 4, ["zus_skill_a", "zus_skill_b"], "zus_example", "png"),
    },

    skill: {
        zus_skill_a: { /* ... */ },
        zus_skill_b: { /* ... */ },
    },

    translate: {
        zus_example: "示例",
        zus_skill_a: "技能甲",
        zus_skill_a_info: "……",
    },

    title: {
        zus_example: "称号",
    },

    sort: {
        zusfylri_example: ["zus_example"],
    },
};
```

## 2. 护甲写法

当前如果要与官方角色包对齐，优先使用：

- `hp`
- `maxHp`
- `hujia`

而不是旧兼容写法 `"2/2/1"`。

如果当前模块的 `char()` 无法直接表达对象式角色数据，可以单独为该角色改成对象式定义，但要保证图片路径和聚合层兼容。

## 3. 图片路径

当前包的图片统一放在：

- `D:\app\noname\resources\app\extension\Zusfylri武将包\image\character`

如果角色仍走数组式角色数据，通常由模块里的 `image()` / `char()` 自动补图。

如果角色改成对象式数据，图片字段要按当前引擎兼容方式写，不能想当然混用旧 `ext:` 标记链和对象式 `img`。

## 六、技能编写的推荐写法

## 1. 普通触发技

最稳的顺序是：

- `trigger`
- `filter`
- `content`
- 再补 `ai`

推荐：

- `filter` 只做判定
- `content` 再做真正的数据读取和结算

不推荐：

- 在 `filter` 里做大规模牌堆扫描
- 在 `filter` 里做大量 UI 读取
- 在 `filter` 里做复杂对象重建

原因很简单：

`filter` 是最容易因为时点不稳而误判整技不触发的地方。

## 2. 开局技

开局技优先参考官方常用模板：

```js
trigger: { global: "phaseBefore", player: "enterGame" }
```

配套过滤通常类似：

```js
return event.name != "phase" || game.phaseNumber == 0;
```

不要一开始就自己乱选：

- `gameStart`
- `gameDrawAfter`
- `phaseZhunbeiBegin`

除非这个技能语义就是特殊时点。

## 3. `viewAs` 技

如果是固定转化：

- 优先按本体 `看破` 这类技能写
- 保持结构尽量简单

如果是动态转化：

- 优先考虑官方 `chooseButton + backup` 路线
- 不要轻易自己拼一套复杂的动态 `viewAs` 事件链

如果必须用函数式：

```js
viewAs: function (cards, player) { ... }
```

那要格外注意：

- 传进来的 `cards` 不一定是干净数组
- 不要默认 `cards[0]` 一定存在
- 不要强依赖 `suit / number / color / type`

## 4. 通过 `player.useCard(...)` 拼虚拟牌链

这类技能不要误当成普通 `viewAs` 技来写。

例如：

- 先弃牌
- 再选目标
- 然后 `player.useCard({name:"sha"}, target)`

这更像“手动拼一条虚拟出牌链”，不是标准转化技。

这类技能重点检查：

- 目标合法性
- 是否计入次数
- 是否与普通牌结算完全一致
- 是否还能触发相关后续技能

## 5. 标记技

推荐原则：

- 标记本体和触发技能尽量分开
- 真正显示标记的 skill 单独写 `marktext / intro`
- 数量变化时明确：
  - `markSkill(...)`
  - `unmarkSkill(...)`

不要只改 storage，却不主动更新 UI 标记。

## 七、当前项目里最该遵守的安全写法

## 1. 运行时对象要现取

优先用：

- `globalThis.lib`
- `globalThis.game`
- `globalThis.ui`
- `globalThis.get`
- `globalThis._status`

不要默认模块加载时拿到的：

- `lib`
- `game`
- `ui`
- `get`
- `_status`

在后续实机事件里仍然是对的。

## 2. 牌对象字段不要默认完整

当前实机里已经反复验证过会丢：

- `color`
- `type`
- `subtype`

所以推荐统一走安全函数：

- `safeName`
- `safeColor`
- `safeType`
- `safeSubtype`

如果当前模块没有抽公共安全层，也至少在本模块里做一层多段兜底。

## 3. step 间共享数据写进 `event`

不要这样想：

- `step 0` 里定义了 `var target`
- `step 1` 一定还能用

在无名杀里这非常危险。

推荐这样：

```js
event.myTarget = target;
event.myCard = card;
event.myInfo = info;
```

然后后面的 step 只读 `event.xxx`。

## 4. 回调里不要依赖局部 helper

高危位置：

- `chooseTarget.ai`
- `chooseButton.ai`
- `filterCard`
- `mod.aiUseful`
- `mod.aiValue`
- `intro.content`
- 各类 `step` 回调

这类位置如果必须复用 helper，优先：

- 挂到 `globalThis`
- 或者直接内联

不要把 helper 半悬在模块局部作用域里。

## 八、什么时候应该用旧架构思路

下面这些情况，优先按旧架构思路写更稳：

1. 技能本身并不复杂  
例如：
- 简单触发
- 简单摸牌/弃牌/加伤/回血

2. 技能 heavily 依赖引擎原生事件链  
例如：
- 开局技
- `viewAs`
- `chooseToUse`
- `chooseToRespond`
- 无懈链

3. 技能已经有旧包稳定版本  
这种情况下最优策略通常不是“重新设计”，而是：

- 先确认旧版本意
- 再按当前引擎可稳定运行的方式重落一遍

一句话：

`旧架构的价值，不在于它旧，而在于它更贴原生。`

---

## 九、什么时候应该用新架构优势

新架构更适合承载这些东西：

1. 模块组织
- 一个武将/一组武将放一个模块
- 统一管理角色、技能、翻译、称号、排序

2. 公共安全层
- `safeColor`
- `safeType`
- `runtimeLib`
- `runtimeGame`

3. 公共开发规范
- 命名规则
- 图片路径规则
- 文案规则
- AI 规则

4. 公共日志/测试辅助
- 实机日志出口
- 单机测试钩子
- 临时诊断函数

也就是说：

`新架构最该承载的是“组织能力”和“安全层能力”，而不是把每个技能本体写得越来越抽象。`

## 十、推荐的写武将 checklist

每写完一个新武将，至少过一遍这张表：

1. 角色数据
- 势力对不对
- 体力/上限/护甲对不对
- 图片路径对不对
- 选将列表能否正常出现

2. 技能触发
- trigger 对不对
- filter 会不会过严
- content 是否真的进入

3. 牌对象
- 是否依赖 `color/type/subtype`
- 是否做了安全兜底

4. step/回调
- 是否跨 step 复用了局部变量
- 是否在高危回调里用了局部 helper

5. UI
- 技能按钮是否出现
- 目标选择是否能正常点
- 标记是否同步
- 数量归零时是否移除

6. AI
- 是否会正常使用
- 是否会乱用
- 是否会对自己乱开

7. 实机
- 脚本级没问题不算完
- 至少做一次真实客户端手测

---

## 十一、最后的总原则

如果只记一句话，就记这一句：

`在这个项目里，真正稳的写法不是“抽象最多的写法”，而是“外层结构清楚，内层技能朴素，关键运行时有安全兜底”的写法。`
